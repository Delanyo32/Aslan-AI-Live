# Product Requirements Document
## NewsTrader AI — AI-Powered News Backtest Platform

**Version:** 0.5
**Status:** For Review
**Asset Classes:** US Stock Market only (V1) — all other markets deferred to V2+
**Target Users:** Retail traders, serious individual investors, small hedge funds & prop traders

> **Scope Note:** This version covers the V1 product — a standalone backtest creation and sharing platform. Live trading and alerts are deferred to V2. V1 is scoped exclusively to the US stock market (NYSE and NASDAQ-listed equities). Crypto, forex, futures, options, and international markets are all "Coming Soon." This keeps the data stack clean and the product story simple at launch.

---

## 1. Problem Statement

Most traders lack the infrastructure to systematically test whether acting on a news event would have been profitable. They rely on gut instinct, scattered tools, and no way to verify their hypotheses against real historical data. There is no accessible, unified platform that lets a trader say _"what would I have made if I traded semiconductor stocks every time the US announced chip export restrictions?"_ and get a credible, sourced, shareable answer in minutes.

---

## 2. Product Vision (V1)

NewsTrader AI V1 is a web-based backtest platform where users describe a news-driven trading hypothesis in plain English, and the AI does the research — finding historical instances of the event, identifying affected instruments, generating a simulated trade log, and returning a full sourced report with P&L. Reports can be saved and shared publicly, creating a viral loop that drives lead generation.

The primary business goal in V1 is email and account capture through a compelling, shareable free experience. Live trading and alert execution are roadmap features surfaced as "Coming Soon."

The primary acquisition surface, accessible without login.

**User Flow:**

2. User types a hypothesis in plain English (e.g., _"Buy Nvidia every time the US announces new AI chip restrictions on China"_)

5. Full report is gated behind an **email capture modal**
6. After email: full backtest report revealed in-browser and emailed as a shareable link
7. User is prompted to create a free account to save reports, run more backtests, and share

**Teaser (Pre-Email):**
- Total return across all events (e.g., "+184% across 7 events")
- Date range covered
- Blurred/partial trade log — first 2 rows visible, rest locked
- Social proof: _"Join X traders who ran this backtest"_

**Full Report (Post-Email):**

The report is a single scrollable page structured as follows, top to bottom:

**① Disclaimer Banner (always visible, cannot be dismissed)**
A persistent, clearly styled banner at the top of every report — both in-app and on the public shared URL — reading:
> _"This report was generated by AI and is for informational purposes only. It does not constitute financial advice. AI-identified events and simulated trades may be inaccurate or incomplete. Past hypothetical performance does not guarantee future results. Always do your own research."_

**② Query & Parameters Block**
Full transparency on what was run, so any reader can evaluate the methodology:
- The exact query the user typed (verbatim)
- Clarifying answers provided by the user (e.g., "Entry: market open next day", "Exit: end of day", "Position size: $10,000 per trade")
- Instruments selected (tickers or ETFs, with rationale)
- Date range searched
- Number of historical event instances found
- Confidence filter applied (e.g., "High and medium confidence events only")

**③ Research Narrative**
2–4 paragraphs of plain-English explanation: what the event is, why these instruments were chosen, a brief summary of the historical pattern observed. Written by the AI, clearly labeled as AI-generated.

**④ Historical Occurrences — Per-Event Detail**
One section per identified historical event occurrence, ordered chronologically. Each occurrence contains:
- Event date and a short description (1–2 sentences)
- Primary source: article headline + publication + URL
- Secondary sources if available
- Confidence level (High / Medium)
- **Impact window summary** for this occurrence: how long the event moved prices, when/why the window ended (mean reversion or override event), and the peak cumulative abnormal return detected
- **Per-ticker subsections** — one for each confirmed ticker in the backtest:
  - A **price chart** covering the event impact window (plus 5 days pre-event for context), with:
    - Entry point marked (▲)
    - Exit point marked (▼)
    - Hold period shaded
    - The impact window end date marked (dashed line) with a label if an override event caused it
    - Benchmark (SPY) overlaid as a secondary line for abnormal return context
  - Trade detail: entry date, entry price, exit date, exit price, direction, hold duration, P&L ($), P&L (%), abnormal return vs. benchmark

The entry/exit markers reflect the trade parameters the user selected. If the user selected a preset (Aggressive / Moderate / Conservative), the preset name is shown on the chart.

**⑤ Aggregate Performance**
- Cumulative portfolio value chart across all events (starting from a $10,000 base or user-defined notional), showing the portfolio value after each trade closes
- Total return ($) and total return (%)
- Win rate (% of trades that were profitable)
- Max drawdown
- Average hold duration
- Best trade and worst trade (highlighted)
- Final portfolio value (prominent, large text — this is the number users share)

**⑥ Full Trade Log Table**
Every simulated trade, every ticker, every occurrence — no omissions. Sortable by any column.

## 6. AI Pipeline (Internal)

### 6.1 Query Understanding & Disambiguation

**Input:** User's plain-language hypothesis

**Steps:**
1. Extract structured intent: event type, instrument hints, direction hypothesis, time range, geography
2. Score ambiguity — flag underspecified components
3. Surface 1–3 clarifying questions if ambiguity is high (skippable — defaults to best-effort run)
4. Always ask the following **trade parameter questions** before executing — these directly affect what gets charted and how open/close markers are rendered on each event chart:
   - _"When should the trade open?"_ (e.g., market open next day / immediately on news / custom delay)
   - _"When should the trade close?"_ (e.g., end of same day / after N days / at a % target or stop)
   - _"What direction?"_ (Long / Short / Let the AI decide based on event sentiment)
   - _"How much per trade?"_ (default $10,000 notional, user can override)
5. Produce structured event spec: `{ event_type, instruments_hint, direction, entry_rule, exit_rule, position_size, date_range }`

### 6.2 Instrument Identification

**Input:** Structured event spec

A single backtest query can target one stock or multiple stocks simultaneously. For example, "trade semiconductor stocks after US chip export restrictions" should generate trades across NVDA, AMD, INTC, and QCOM in parallel — not just one ticker. Multi-stock backtests are a first-class concept, not an edge case.

**Steps:**
1. Reason over which US-listed tickers or sector ETFs are most correlated to the event type
2. Distinguish between:
   - **Single-stock queries** (user names a specific company) → one ticker
   - **Sector or theme queries** (user names a theme, sector, or group of companies) → multiple tickers, up to a configurable cap (default max: 10 tickers per backtest to bound compute cost)
3. Return a ranked list with a one-line rationale per instrument — ordered by estimated relevance to the event
4. User reviews, confirms, removes, or adds tickers before the backtest executes
5. The confirmed ticker list is recorded verbatim in the report's Query & Parameters block

### 6.3 Historical Event Detection

**Input:** Structured event spec + confirmed instrument list

This is the most critical step. The strategy is to use the two available data sources in sequence — structured financial news first, broad semantic web search second — before deciding whether a vector DB is warranted.

**Step 1 — Alpaca News API (Benzinga corpus):**
- Query by ticker symbol and date range to retrieve all relevant articles
- Score each article against the event spec using the LLM
- Cluster matches by event date — each unique occurrence = one backtest data point
- This covers equity-specific news well back to 2015

**Step 2 — Exa.ai (Web Search):**
- Run a semantic query formulated from the event spec against the broader web
- Captures macro events, regulatory announcements, geopolitical catalysts, and events not well-covered by Benzinga
- Cross-references results against Step 1 to avoid duplicates and validate dates
- Returns source URLs and headlines for citation

**On the Vector DB question:**
A custom vector DB (e.g., pgvector, Qdrant) over the Alpaca/Benzinga corpus would allow semantic search without a per-query cost to an external API. This is a meaningful optimization at scale — if a user query cannot be satisfied by symbol-tagged articles alone (e.g., a macro event with no specific ticker), a self-hosted semantic index would be faster and cheaper than an Exa.ai call. However, Exa.ai's own index effectively provides this capability without the operational overhead of running and maintaining a vector store. **The recommendation for V1 is to not build a custom vector DB — rely on Alpaca's structured news API for ticker-specific lookups and Exa.ai's semantic index for broader discovery.** Introduce a self-hosted vector DB in V2 only if Exa.ai per-query costs become a meaningful cost line.

**Event confidence scoring:**
- High: event date confirmed by ≥2 sources, ticker clearly implicated
- Medium: single source match, ticker inferred
- Low: date uncertain or ticker connection weak
- Default: only high/medium matches included in backtest; low-confidence shown as a toggle

### 6.3b Event Impact Window Detection

**Input:** Event timestamps + confirmed ticker list + Alpaca OHLCV data

This step runs after historical events are identified and before the user is asked about entry/exit. Its purpose is to calculate, for each event occurrence and each ticker, how long the event actually moved the price — and when that effect ended. This analysis is what enables the platform to offer intelligent, data-driven entry and exit suggestions rather than arbitrary time-based defaults.

**What "impact window" means:**
The impact window for a given event-ticker pair is the continuous period of abnormal price movement attributable to that event, bounded by either:
- **A subsequent news event** on the same ticker that materially changes the price direction (detected via the Alpaca News API — an override event)
- **Mean reversion** — the ticker's abnormal return (price movement relative to the S&P 500 or sector index on the same days) decays back toward zero, signalling the event's effect has been fully priced in
- **A maximum cap** of 30 trading days — if neither boundary is detected, the window closes at 30 days

**How it is calculated (per event, per ticker):**
1. Fetch daily OHLCV bars from Alpaca Market Data for the ticker, starting from the event date, for up to 30 trading days forward
2. Fetch the same date range for a benchmark (SPY for most stocks; sector ETF if the query is sector-specific)
3. Compute daily **abnormal return** = ticker daily return − benchmark daily return
4. Compute **cumulative abnormal return (CAR)** from event date forward — this is the running total of the price movement attributable to the event
5. Detect the window end using two signals, whichever comes first:
   - **Override event:** scan the Alpaca news corpus for a headline on the same ticker within the window that scores above a relevance threshold and has an opposing sentiment to the original event → window ends the day before this headline
   - **CAR decay:** CAR crosses back through zero (full mean reversion) or drops below 20% of its peak value (significant decay) → window ends at that day
6. Record: `{ impact_start, impact_end, impact_duration_days, peak_CAR, peak_CAR_date, final_CAR, override_event (if applicable) }`

**Output — Entry/Exit Suggestions:**
After the impact window is calculated for each event occurrence, the AI generates three suggested trade configurations, presented to the user before they finalise their backtest parameters:

| Option | Entry | Exit | Based On |
|---|---|---|---|
| **Aggressive** | Market open on event day | Peak CAR date (when abnormal return was highest) | Catches maximum upside but requires fast execution |
| **Moderate** | Market open next trading day | Event impact end date (CAR decay or override event) | Rides the full event effect with a 1-day entry buffer |
| **Conservative** | Market open 2 days after event | Fixed 5 trading days after event | Avoids gap-open noise; trades the sustained trend only |

The user can select one of these presets or enter custom entry/exit rules. The selected option (or custom parameters) is recorded in the report's Query & Parameters block and used for all trade simulations.

**Multi-stock behaviour:**
When the backtest covers multiple tickers, the impact window is calculated independently per ticker per event occurrence. Entry/exit suggestions are shown as a combined view — e.g., "For this event, NVDA's impact lasted 8 days; AMD's lasted 14 days; INTC reversed after 3 days due to an earnings override." The user applies one entry/exit rule uniformly across all tickers in V1 (per-ticker rules are a V2 feature).

### 6.4 Trade Simulation

**Input:** Event timestamps + confirmed ticker list + event impact windows + user-selected entry/exit rule

**Multi-stock behaviour:**
Each event occurrence generates one trade per confirmed ticker. For example, if 7 historical event occurrences are found and the user confirmed 4 tickers, the backtest produces up to 28 simulated trades. All trades are included in the report — none are hidden or summarised away.

**Entry/Exit Resolution:**
The user's chosen entry/exit rule (from the three presets or custom) is applied consistently across all tickers and all event occurrences. Entry and exit prices are resolved against actual OHLCV data from Alpaca:
- "Market open" entries use the open price of the relevant session
- "Peak CAR date" exits use the close price on that date
- "Impact end date" exits use the close price on the day the window closed
- All legs subject to 0.1% slippage

**Per-trade record:**
`{ event_date, ticker, direction, entry_date, entry_price, exit_date, exit_price, hold_days, impact_window_end, override_event (if applicable), P&L_dollars, P&L_pct, abnormal_return_vs_benchmark }`

**Portfolio accounting (multi-stock):**
- Each trade is sized equally at the user's configured notional (default $10,000) regardless of ticker
- Trades on different tickers triggered by the same event occurrence run concurrently — portfolio value reflects all open positions at any point in time
- The cumulative portfolio chart plots running portfolio value day by day across the full backtest period, including overlapping positions

### 6.5 Report Generation

**Input:** Full trade log (all tickers, all occurrences) + event list + impact window data + source URLs + AI reasoning trace + user's original query + confirmed trade parameters

**Output sections (mirrors §5.1 Full Report spec):**
- Non-dismissible disclaimer banner
- Query & parameters block (verbatim query, confirmed answers, tickers with rationale, entry/exit preset or custom rules, date range, confidence filter)
- AI-generated research narrative (2–4 paragraphs, labeled as AI-generated)
- Per-occurrence sections: one block per historical event, containing per-ticker charts and trades (see §5.1 ④)
- Aggregate performance across all tickers and all occurrences: cumulative portfolio value chart, total return, win rate, max drawdown, avg hold, best/worst trade, **final portfolio value**
- Full sortable trade log table — every trade, every ticker, no omissions
- Complete sources list

## 7. Data Stack (Simplified)

The V1 stack uses exactly three external data services. No more.

```
┌─────────────────────────────────────────────────────┐
│                   NewsTrader AI                      │
│                                                      │

│  │  News API    │  │ Market Data  │  │   (Web    │  │
│  │  (Benzinga)  │  │  API (OHLCV) │  │  Search)  │  │
│  │              │  │              │  │           │  │
│  │ News corpus  │  │ Price data   │  │ Semantic  │  │
│  │ 2015–present │  │ 5+ yrs hist  │  │ discovery │  │
│  │ ~130 art/day │  │ Equities +   │  │ macro +   │  │
│  │ Ticker-tagged│  │ Crypto       │  │ broad web │  │
│  └──────────────┘  └──────────────┘  └───────────┘  │
│        ▲                  ▲                ▲         │
│        └──────────────────┴────────────────┘         │
│                    AI Pipeline                        │
└─────────────────────────────────────────────────────┘
```

| Role | Provider | What It Covers | What It Doesn't Cover |
|---|---|---|---|
| **News** | Alpaca (Benzinga) | US equities news, 2015–present, ticker-tagged, REST + WebSocket | Crypto, forex, futures, international markets, deep macro not tagged to a ticker |
| **Price Data** | Alpaca Market Data | US equities OHLCV, 5+ years historical, real-time streaming | Crypto, forex, futures (all deferred to V2+) |
| **Web Search** | Exa.ai | Semantic search across the broader web; macro events, regulatory announcements, anything outside Benzinga's corpus | Not a structured financial data source — discovery + citation only |

**Why Exa.ai over Tavily for the web search slot:**
Tavily was acquired by Nebius in February 2026, introducing pricing and roadmap uncertainty. More importantly, the core challenge here — finding news events from 2015 to present where the same type of event was described in many different ways across years — is a semantic retrieval problem, not a keyword search problem. Exa.ai's neural search index is built for this. Tavily remains a viable fallback option and can be swapped in without architecture changes if needed.

**Forex / Futures — V1 Position:**
Alpaca's price data API does not currently support forex or futures (noted as on their roadmap). To keep the V1 stack at three services, forex and futures backtests are deferred to V2. When Alpaca adds forex/futures data, this slot fills naturally. The "Coming Soon" UI surface on the backtest tool should include forex and futures as a teaser to generate interest and validate demand.

## 11. Open Questions

1. **Compliance copy:** The non-dismissible disclaimer on every report (in-app and shared URL) is the primary protection mechanism. Confirm with legal counsel whether the specific wording is sufficient for the target jurisdiction before launch, and whether the shareable public URL format requires additional disclosures.
2. **Backtest confidence floor:** What is the minimum number of historical event instances required before showing results? 1–2 events produce statistically meaningless results. Define the floor and the UX for when it's not met (e.g., "Only 1 instance found — results may not be representative. Run anyway?").
3. **Exa.ai pricing at scale:** Confirm per-search pricing and committed volume discounts. Model cost per backtest before locking in.
4. **Alpaca plan tier:** Confirm which Alpaca plan tier covers historical news + OHLCV access for the use case. The free plan limits real-time equity data to IEX — verify historical data is not similarly restricted.
5. **Impact window — CAR decay threshold:** The 20%-of-peak decay threshold for impact window end is a starting assumption. This should be validated against real historical event data before launch — the threshold may need tuning per event type (e.g., earnings events typically revert faster than regulatory events).
6. **Multi-stock ticker cap:** The 10-ticker default cap is a cost-control measure. Confirm whether this is the right limit given the credit system, or whether higher-credit tiers should unlock a higher cap.
